# Согласованные правила новой версии

Приложение запускается открытием `galamart-analyst/index.html` в браузере через `file://`. Сервер и сборка для работы не нужны. Распространяется вся папка `galamart-analyst`, включая `js`, `lib` и CSS. Старые HTML-точки входа перенаправляют в соответствующий раздел единой версии; для них нужна соседняя папка `galamart-analyst`. Перед переходом со старой самостоятельной Suadela следует выгрузить её JSON и при необходимости восстановить его в новой версии.

## Отчёт и остатки

Единственный основной источник — «Остатки по датам ввоза». Импорт заменяет текущий рабочий отчёт; история сохраняемых директорских снимков разных дат остаётся. Дубли кодов и неверные даты отклоняются. Возраст остатков рассчитывается на дату остатков из заголовка, срочность уценки — на дату проведения уценки. Продажи охватывают 28 дней; иной явно указанный период отклоняется.

Скорость преимущественно берётся из поля «Остатки, дней»: остаток / дни. Значение 9999 означает бесконечный запас. При отсутствии показателя возможна оценка по продажам / 28, а не по возрасту ввоза.

Мёртвый сток: положительный остаток, возраст ввоза не меньше 28 дней, отсутствие продаж в отчёте. Это доступный по снимку признак, а не доказательство отсутствия продаж за всю жизнь артикула.

Медленный сток: с даты последней поставки прошло не меньше 28 дней, положительный остаток и `продано за 28 дней / (остаток + продано за 28 дней) < 0,2 × 28 / 21` (26,666…%). Показатель приблизительный: предполагает равномерные продажи и отсутствие поступлений, списаний и других движений. Мёртвый сток может одновременно входить в медленный. Дневная история не требуется.

Показываются запас в днях по штукам и по себестоимости: `стоимость остатка / (ТО СС / 28)`. Это показатели покрытия текущего остатка, не классическая оборачиваемость по среднему запасу.

Фактическая ВП предварительно определяется как `ТО − ТО СС`. Требуется внешняя сверка значения ТО СС с контрольным отчётом 1С. Отдельные возвратные строки отображаются отдельно; возвраты, уже свёрнутые внутри положительной итоговой строки 1С, из такого отчёта восстановить нельзя.

## Уценка

«Клизма»: дата ввоза не позднее выбранной, кроме категории «НЕ клизма», только положительный остаток. Дедлайн — ближайшее 15-е число, включая сегодня. После 15-го — 15-е следующего месяца. Переоценки только вторник/пятница. Последняя разрешённая переоценка перед дедлайном — 1 ₽. Если она пропущена, интерфейс сообщает об этом и не предлагает переоценку вне расписания.

«Продать до»: выбранная дата отбирает товары, срочность определяется собственной датой окончания продаж каждого товара. В последний день — 1 ₽ независимо от дня недели. Просроченный остаток выделяется.

При достаточном темпе текущая цена сохраняется, кроме обязательной финальной переоценки. Промежуточная скидка — эвристика с пересмотром по вторникам/пятницам, не гарантия роста спроса. При бесконечном запасе: `20% + 50% / число оставшихся переоценок`, максимум 70%. При недостаточном темпе используется давление остатка к сроку: `1 − (1 / отношение)^0,6`, минимум 20%, максимум 90%; учитывается интервал до следующего пересмотра. Рекомендация не повышает цену. Рекомендации на будущий разрешённый день явно подписаны.

Округление вниз: ниже 1000 ₽ — окончание 9,90; от 1000 ₽ — целая цена с последней цифрой 9. Если округление пересекает границу 1000 ₽, допустимо 999,90. Ниже 9,90 — окончания 0,90, минимум 1 ₽. Ограничения по себестоимости нет.

Экспорт товарных списков: только артикулы; артикулы с новыми ценами; только цены, явно изменённые пользователем; полная отфильтрованная таблица. Экспорт охватывает весь отбор, а не только видимую страницу. Пустая, нечисловая цена или цена ниже 1 ₽ блокирует соответствующий экспорт цен.

## 3SKU и продажи

Порог определяется выполнением плана соответствующей SKU всем известным продавцам. До порога — штуки × ставка продавцу. После порога дополнительно начисляется фонд на все штуки, распределяемый пропорционально количеству. Пример: план 100, порог 80%, ставка 5, фонд 2: 70 шт. → 350 ₽; 80 → 560 ₽; 100 → 700 ₽.

Минимальная выплата применяется отдельно к каждой паре «продавец + SKU» после добавления фонда. Ниже минимума сумма не выплачивается и не переносится. При минимуме 500 ₽ начисления 400 и 600 по разным SKU дают выплату 600 ₽.

Неопределённые/не включённые в справочник продавцы не участвуют в плане и начислениях. Возвраты не влияют на мотивацию, в продажах показываются отдельно. Повторный импорт дня полностью заменяет прежний; при нескольких выбранных файлах одной даты побеждает последний.

Прогноз выполнения плана **3SKU** — по всем прошедшим календарным дням, с отдельными периодами активности SKU. Графики рабочих смен пока не учитываются. Общий требуемый темп — сумма требуемых темпов позиций. Незагруженные дни неизвестны, загруженные без продаж — нули. День переоценки относится к периоду «после». Переоценки в «Продажах» используют до 28 календарных дней с каждой стороны события с ограничением соседними переоценками; для сравнения нужны наблюдения с обеих сторон. Этот алгоритм отличается от прогноза плана 3SKU.

«3SKU на 100 чеков» = штуки / вручную введённые чеки × 100. Отдельно по каждой позиции и суммарно; это не доля чеков с товаром. Источник общих чеков выбирается отдельно по дням: введённый итог магазина, иначе сумма кассиров.

## Зоны, R29, подарки и Vision

Дозаказ: прогноз остатка к ближайшей поставке; целевой запас = норма выкладки артикула + продажи за неделю до следующей поставки. Трансфер, резерв и оптовый остаток не учитываются. КУБ с «ЗО» запрещает поставку; ВнеАМ предупреждает о невыгодности. Итоги объединённых зон считают артикул один раз.

R29 группирует по цене; перенос между зонами не меняет фактические ТО/ВП. Для факта нужны колонки ТО и ТО СС в input2. Если их нет, строки и итоги обозначаются неполными; текущая цена не подменяет историю продаж.

Подарки отбираются по себестоимости. Добавлены фильтры ЗО, ЗО сеть, ВнеАМ, мёртвого и медленного стока.

Vision: абсолютные значения сравниваются со средним магазином выборки, финансовые доли/выполнение планов — отношениями сумм сопоставимых исходных данных. Неизвестные значения не считаются нулями. Прошлый год для магазина берётся из отчёта, без жёстко подписанного 2025 года. Выбранный магазин входит в сетевую выборку.

## Проверка и упаковка

`npm ci`, затем `npm test` — проверки правил и хранения. `npm run test:browser` — Chromium через file://: интерфейс, импорт, расчёты, сохранение после перезагрузки, печать R29. Путь Chromium задаётся `CHROME_BIN`, по умолчанию `/usr/bin/chromium`. Если рядом есть предоставленный отчёт остатков, он также проверяется браузерным тестом.

`npm run sync:android` обновляет веб-ассеты Android. Gradle также синхронизирует их перед сборкой; исходные Excel в APK не включаются. Браузерная проверка не заменяет проверку APK на устройстве.

## Рабочее место директора

Дополнительные правила контроля цен, истории снимков, оценки рисков и заданий описаны в [DIRECTOR_GUIDE.md](DIRECTOR_GUIDE.md). Данные директора хранятся отдельно; основной импорт по-прежнему заменяет рабочий отчёт. Фильтр КУБов в подарках — множественный: выбранные значения объединяются по «или», без выбора доступны все.

Цена ниже или выше ТН сама по себе не является проблемой. Контроль отклонений доступен через фильтры. При любой указанной дате окончания продаж дозаказ исключён. Нормы одного SKU в нескольких коммерческих зонах суммируются. Замены по умолчанию подбираются по группе второго уровня с возможностью расширить отбор.

## Продажи, прогноз и переоценки

Подробные источники и ограничения: [SALES_GUIDE.md](SALES_GUIDE.md). Себестоимость для продаж берётся из текущего отчёта остатков; ВП прошлых дат — оценка. Неизвестная себестоимость не заменяется нулём. Пропущенные отчёты не являются нулевыми продажами. При импорте продажи и возвраты одного SKU/продавца/дня сохраняются раздельно. Прогноз различает спрос и продажи, обеспеченные запасом, не придумывает поставки. Переоценка регистрирует дату и две цены одного SKU; сопоставляет загруженные дни до/после и одинаковые дни недели.

Подтверждено пользователем: исходная иерархическая выгрузка с сотрудниками содержит **весь ассортимент и суммы**, а 3SKU отбирает из неё акционные артикулы. «Продажи» и 3SKU используют один импорт и историю; подробная структура источника описана в SALES_GUIDE.md.
